# Architecture

This guide maps the stable mathematical boundaries and public import surfaces
of `cubical-classics`. It describes the checked source tree, not temporary
implementation plans. For contribution workflow and verification commands,
use the [development guide](DEVELOPMENT.md).

## Assumption Boundary

The top-level split is semantic, not merely organizational.

- `Constructive` modules must not import `Classical` modules or use the
  library's `Oracle`.
- `Classical` modules may use `Oracle`, excluded middle, choice, resizing, and
  impredicative powerset interfaces. The assumptions remain visible in module
  or theorem parameters.
- Classical developments may reuse constructive algebra, completions, and
  analysis. Dependencies must not point in the opposite direction.

At a high level, dependencies flow as follows:

```text
Cubical
  ├──> Constructive foundations and data
  │       └──> Constructive algebra
  │               └──> Constructive completions and analysis
  └──> Classical axioms

Constructive mathematics + Classical axioms
  └──> Classical foundations, completions, topology, and analysis
```

`Solvers` contains proof automation used by the mathematical layers. It does
not define a separate assumption boundary.

| Area | Responsibility |

| `Constructive.Algebra` | Ordered algebra, Archimedean structures, morphisms, instances, and univalence. |

| `Classical.DedekindCut` | Oracle-based cut completion and its universal property. |
| `Classical.Topology` and `Classical.Analysis` | Classical topology and exact real-analysis theorems. |

## Completion And Real Boundaries

### Cauchy completion

[`Constructive.Analysis.Completions.CauchyCompletion`](../Constructive/Analysis/Completions/CauchyCompletion.agda)
is the generic HoTT-style completion interface. It owns the completion type,
closeness, induction and recursion, metric-space packaging, completeness, and
extension principles.

[`Constructive.Analysis.Reals.CauchyReals`](../Constructive/Analysis/Reals/CauchyReals.agda)
specializes that construction to the rational metric space. Its main type
`ℝᶜ` is generated by rationals and limits of precision-indexed Cauchy
approximations; it is not presented as a quotient of rational Cauchy sequences.
Real-specific arithmetic, order, and Archimedean results belong in this
specialization rather than the generic completion.

### Dedekind completion

[`Constructive.Analysis.Completions.DedekindCompletion`](../Constructive/Analysis/Completions/DedekindCompletion.agda)
is the generic constructive two-sided located-cut completion over a linearly
ordered field and owns its generic order, approximation, and completeness
interfaces.

[`Constructive.Analysis.Reals.DedekindReals`](../Constructive/Analysis/Reals/DedekindReals.agda)
is the rational instance and preserves the public `ℝᴰ` interface.
[`Constructive.Analysis.Reals.Comparison`](../Constructive/Analysis/Reals/Comparison.agda)
contains comparison maps between constructive real presentations.

[`Classical.DedekindCut`](../Classical/DedekindCut.agda) is a separate,
Oracle-based completion of an Archimedean ordered field. Do not use it as a
replacement for the constructive completion. Conversely,
[`Classical.DedekindCompletion`](../Classical/DedekindCompletion.agda) proves
classical MacNeille completeness for the constructive completion under
`Oracle`.

### Constructive analysis data

The generic metric API is indexed by positive rational precision. Real-specific
locatedness, interval, sequence, IVT, series, and power-series interfaces live
under `Constructive.Analysis.Reals`.

A bare Cauchy real, a located Cauchy real, and a real supplied with explicit
rational bounds support different theorem statements. In particular, a
truncated existence proof must not be silently strengthened into a reusable
modulus. The [HoTT and Bishop analysis note](BISHOP_ANALYSIS.md) owns this
distinction and the corresponding power-series design rules.

Exact compactness and IVT statements that require classical reasoning remain
under `Classical.Analysis`; constructive modules expose the precision-indexed
or approximate forms justified by their data.

## Public Versus Internal Modules

A file's existence does not by itself make it a stable dependency.

- Prefer the documented aggregate for ordinary downstream imports.
- A module reexported with `public` is part of that aggregate's surface.
- A direct module documented above may be used when no suitable aggregate
  exists or when the aggregate deliberately omits it.
- Modules or directories named `Internal`, local helper modules, and proof
  plumbing are implementation details unless a public aggregate explicitly
  promotes their declarations.
- A file whose name matches a directory is not necessarily an aggregate. Read
  its imports before assuming that it reexports the directory.

When a stable module path, documented role, or architectural boundary changes,
update this guide in the same change. Exact aggregate import lists stay in the
Agda source and do not need to be copied here. Update the
[project README](../README.md) only when its short stable-entry list or the
user-facing mathematical story changes. Do not expand either document into an
inventory of every helper or theorem.
